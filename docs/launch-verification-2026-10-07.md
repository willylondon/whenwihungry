## Actual deployed database findings

1. `profiles` has RLS but authenticated table-wide INSERT/UPDATE plus own-row policies. There is no role-protecting trigger. This permits self-promotion at the SQL policy/grant level. A synthetic reconstruction reproduced it; no production account was promoted to test it.
2. `admin_reviews`, `user_reviews`, `dishes`, `search_keywords`, `search_logs` have RLS **disabled** and broad grants for `anon` and `authenticated`, including writes and TRUNCATE. Advisor shows five critical RLS issues. `search_logs` is particularly unsuitable for anonymous access.
3. Signup `handle_new_user` assigns admin based on email text. The draft replaces that with user-only signup; existing operator-assigned roles remain unchanged.
4. Actual critic columns include `headline`, `honest_take`, `reviewed_at`; **visit_date is missing**. `restaurants.review_status`, both price columns, and the unique critic restaurant constraint exist. Historic review timestamps must not be used to invent visit dates.

Deployed migration history contains only six entries: `platform_foundation`, `tighten_score_function_security`, `profile_creation_and_seed_restaurants`, `revoke_public_function_execute`, `admin_listing_moderation`, `add_scrape_metadata_columns`. The two original PR migrations and the new baseline migration are unapplied; `review_requests` and `publish_critic_review` are absent.

The new CLI-generated draft `20261007120640_verified_launch_security_baseline.sql` closes these observed gaps. It restricts profile writes to display names, removes signup promotion, enables RLS and explicit role policies on all five tables, denies public logs/anonymous writes/TRUNCATE, restricts moderated review submissions, protects listing flags/ratings from ordinary users, permits admin-created pending listings, adds nullable visit dates without backfilling them, and closes superseded direct writes to legacy ratings/comments.
